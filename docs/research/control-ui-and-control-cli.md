## Finding

These are two instruction-only Agent Skills, not Cursor built-ins, MCP tools, installed executables, or wrappers around a fixed service. Each directory contains only `SKILL.md`. The examples are templates with placeholders. The plugin ships no `control-ui` or `control-cli` executable, package dependency, MCP configuration, simulator driver, or process daemon. Cursor installs the containing plugin with `/add-plugin cursor-team-kit`; its README calls both components skills. [plugin README, lines 3-9 and 13-24](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/cursor-team-kit/README.md#L3-L24) [local README](file:///tmp/cursor-plugins-pstack/cursor-team-kit/README.md#L3-L24)

### `control-ui`

Its contract is to reuse a repository's browser, Playwright, Cypress, Storybook, Electron, or snapshot harness, or build a temporary local harness around a dev server or Chromium debug port. It targets local web, IDE, and Electron UI checks. It reproduces focus, keyboard, scrolling, resize, and rendering behavior and can collect screenshots, accessibility snapshots, console/network logs, traces, CPU profiles, and heap snapshots. [`control-ui`, lines 2-25](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/cursor-team-kit/skills/control-ui/SKILL.md#L2-L25) [local source](file:///tmp/cursor-plugins-pstack/cursor-team-kit/skills/control-ui/SKILL.md#L2-L25)

For ordinary web pages it shows Playwright launching Chromium, navigating to a local URL, selecting by accessibility role, clicking, and saving a full-page PNG. For Electron or another Chromium application it connects Playwright over CDP, enumerates pages, chooses one by a stable app-root marker, and saves a screenshot. The required observation loop is before snapshot, one action, fresh snapshot, asserted state change, and retained before/after artifacts. [`control-ui`, lines 27-82](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/cursor-team-kit/skills/control-ui/SKILL.md#L27-L82)

Raw CDP is reserved for browser-level diagnostics such as tracing, profiling, heap snapshots, request controls, rendering emulation, console capture, and DOM snapshots. The skill prefers roles, labels, and stable `data-*` selectors. It rejects stale references and coordinate clicks unless the click follows a fresh screenshot. [`control-ui`, lines 84-109](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/cursor-team-kit/skills/control-ui/SKILL.md#L84-L109)

There is no bundled accessibility-tree command or visual-diff algorithm. The description promises accessibility snapshots and visual diffs, but the implementation depends on whatever harness the target repository or environment supplies. **Unknown:** support for browser engines other than Chromium, non-Electron native desktop applications, mobile simulators, and remote-device control is undocumented. pstack explicitly assigns native mobile to a repository-specific simulator skill instead. [pstack `multi-phase-plan`, lines 13-15](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/pstack/skills/poteto-mode/playbooks/multi-phase-plan.md#L13-L15)

### `control-cli`

Its contract is to reuse a repository's CLI/TUI test or demo harness, or create a temporary local terminal harness. It drives prompts, keyboard input, interrupts, resize behavior, and terminal layout. It captures transcripts, demos, startup timing, CPU profiles, heap snapshots, and hang diagnostics. [`control-cli`, lines 2-16](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/cursor-team-kit/skills/control-cli/SKILL.md#L2-L16) [local source](file:///tmp/cursor-plugins-pstack/cursor-team-kit/skills/control-cli/SKILL.md#L2-L16)

The process contract is concrete but tool-neutral: launch the command in an isolated terminal with deterministic environment variables, capture the screen, send one input at a time, wait for a specific prompt or screen pattern, retain transcript/profile artifacts, then terminate cleanly. Suggested drivers are a repo-native harness, `tmux`, a temporary Python/Node/Expect PTY probe, Node or Bun's inspector, and an asciinema-compatible recorder. [`control-cli`, lines 18-35](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/cursor-team-kit/skills/control-cli/SKILL.md#L18-L35)

The `tmux` template starts a detached session, reads the pane, sends keys, reads it again, and kills the session. The PTY template uses `pty.openpty`, `subprocess.Popen`, `select`, a deadline, byte-pattern readiness, `os.write`, transcript output, and process termination. Profiling compares baseline and treatment under the same command, machine, and environment; leak checks bracket repeated work with GC and heap snapshots; hang checks capture screen and runtime state before interruption. [`control-cli`, lines 37-101](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/cursor-team-kit/skills/control-cli/SKILL.md#L37-L101)

The templates are illustrative, not a complete process supervisor. **Unknown:** exit-code assertions, ANSI screen normalization, timeout escalation, signal handling, child-process cleanup, transcript format, and video encoding are undocumented. The guardrails require deterministic waits, safe inputs, temporary harnesses under `/tmp`, and cleanup. [`control-cli`, lines 103-109](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/cursor-team-kit/skills/control-cli/SKILL.md#L103-L109)

## Prerequisites and environment

Neither skill requires Cursor Cloud or an external service. Both require the application to run where the agent can execute local commands, plus an applicable harness:

- `control-ui`: a running local web/Electron/Chromium target and existing browser tooling, commonly Playwright. CDP requires a Chromium-family process that accepts `--remote-debugging-port`. The skill says not to add Playwright to the project solely for a probe without user approval. [`control-ui`, lines 18-25 and 27-46](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/cursor-team-kit/skills/control-ui/SKILL.md#L18-L46)
- `control-cli`: the command under test and one available local driver such as the repo harness, `tmux`, Python/Node/Expect PTY support, or a recorder. Inspector profiling additionally needs a supported Node or Bun runtime. [`control-cli`, lines 18-35 and 48-58](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/cursor-team-kit/skills/control-cli/SKILL.md#L18-L58)

Cloud execution comes from pstack policy, not either control skill. Shipping requires one Cursor cloud verifier per PR. Multi-phase plans put every live lane on its own cloud VM. Orchestrate instead defaults workers to cloud but moves verification local when it needs this machine's UI, simulator, IDE state, transcripts, or credentials. These statements are compatible only when a cloud VM can boot the complete target and harness; otherwise pstack's local exception applies. [pstack `shipping`, line 7](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/pstack/skills/poteto-mode/playbooks/shipping.md#L7) [pstack `multi-phase-plan`, lines 69-76](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/pstack/skills/poteto-mode/playbooks/multi-phase-plan.md#L69-L76) [pstack `orchestrate`, lines 17-21](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/pstack/skills/poteto-mode/playbooks/orchestrate.md#L17-L21)

## What pstack requires and why

The main `poteto-mode` router requires the matching control skill when shipping a UI, IDE, or CLI and requires bug fixes to be reproduced first on the same user-facing surface. [pstack `SKILL.md`, lines 24-33](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/pstack/skills/poteto-mode/SKILL.md#L24-L33)

Direct playbook references are:

- `multi-phase-plan`: mandatory live verification in addition to unit and performance checks; ten independent lanes at the exact PR head, each with a scenario, screenshot, and pass predicate; interaction changes also need operator-reviewed screenshots and video. [`multi-phase-plan`, lines 13-15](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/pstack/skills/poteto-mode/playbooks/multi-phase-plan.md#L13-L15)
- `autopilot-full`: no clean merge verdict without an independent lane proving load-bearing behavior live on the changed surface. A changed head invalidates the verdict. [`autopilot-full`, lines 8-9](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/pstack/skills/poteto-mode/playbooks/autopilot-full.md#L8-L9)
- `shipping`: compare parent with head on the real surface, use a verifier who did not write the code, post `PASS`, `PASS+NOTES`, or `FAIL` to the PR, and reject CI or bot approval as sufficient proof. [`shipping`, lines 7-9](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/pstack/skills/poteto-mode/playbooks/shipping.md#L7-L9)
- `orchestrate`: place a verifier locally when runtime proof depends on machine-local resources. [`orchestrate`, lines 17-21](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/pstack/skills/poteto-mode/playbooks/orchestrate.md#L17-L21)
- `opening-a-pr`: name the actual verification path and result, not merely a command, and attach screenshots or video when they prove a claim. [`opening-a-pr`, lines 13-21](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/pstack/skills/poteto-mode/playbooks/opening-a-pr.md#L13-L21)

`autopilot-stack` inherits the same live-runtime floor through swarm verification but does not name either skill directly. [`autopilot-stack`, line 8](https://github.com/cursor/plugins/blob/b9ddc83c32972210b8a94d389130713e8eed346e/pstack/skills/poteto-mode/playbooks/autopilot-stack.md#L8)

The standard being enforced is stronger than "tests pass": fresh runtime behavior at the reviewed SHA, independent observation, explicit pass predicates, retained artifacts, and proof that survives chat. The ten-lane/model requirement is pstack orchestration policy. It is not part of either control skill's contract.

## Codex, Pi, and ds-mode

Both files can load under Codex or Pi without rewriting. They use ordinary `name` and `description` frontmatter and contain no Cursor-only tool calls. Codex defines a skill as a `SKILL.md` directory and discovers repository or user skills under `.agents/skills`; Pi implements the same Agent Skills shape, loads `~/.agents/skills`, and also accepts `--skill <path>`. [Codex skills docs, lines 33-45 and 118-146](https://developers.openai.com/codex/skills#where-to-save-skills) [local Codex docs snapshot](file:///tmp/codex-skills.md#L33-L45) [Pi skills docs, lines 5-39 and 65-99](file:///home/david/.local/share/mise/installs/node/24.18.0/lib/node_modules/@earendil-works/pi-coding-agent/docs/skills.md#L5-L39)

Independent installation is therefore just copying or linking the two skill directories into a supported skill location. Cursor's `/add-plugin` command is not portable. No host adapter or MCP server is needed, but every use still needs the small application-specific harness adaptation the skills explicitly demand. If the environment lacks Playwright, `tmux`, a PTY runtime, or a suitable browser, the corresponding recipe cannot run as shown. **Unknown:** exact support for Codex Cloud, Pi remote workers, native IDE automation, and mobile simulators is undocumented.

## Recommendation for ds-mode

Do not install or retain these as universal workflow dependencies. Replace the pstack names with ds-mode's existing generic rule to exercise the real behavior and keep proportionate, rerunnable evidence. Treat `control-ui` and `control-cli` as optional project-specific skills when a repository repeatedly needs a stable browser/CDP or PTY recipe. This keeps the useful proof standard without importing pstack's fixed ten-lane cloud policy or two mostly generic prompt files.
