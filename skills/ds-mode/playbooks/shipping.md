### Shipping

**You own what lands. Confirm each PR's verdict still holds, land only the verified run from the root, then keep your hands off the rest.**

This is the merge half. [Opening a PR](opening-a-pr.md) already posted each PR's independent verdict.

1. **Every PR needs an independent verdict that still describes its current head.** Use the verdict Opening a PR posted. A PR whose body says it changes no behavior counts as passing once you confirm that against the diff. Any other PR without a verdict gets one now, the same way: a fresh Review worker on the real surface, verdict and evidence posted on the PR. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Re-check that each verdict still describes the patch.** Record the verdict head SHA, base SHA, and stable `git patch-id` of that PR's base-to-head diff. Review fixes, rebases, and base retargets rewrite SHAs and can silently invalidate a verdict without touching a check. Before landing a PR, compare the recorded patch-id with its current base-to-head patch-id. When the two patches differ only in tests, docs, or lint config, build what each lane ran. Build it twice at the verdict SHA and once at the current head. A difference is noise if the two builds at the verdict SHA also show it, or if it is an embedded commit SHA. Judge each difference, not each file, and report each kind of noise with its files. If only noise differs, that lane's result stays valid, and checks and a review of the change run fresh. Do not reuse a lane result from a dev server or from anything else with no build output. Rerun that lane. Re-verify anything else when the patch changed. When it did not, keep the code verdict but re-run mergeability and CI at the current head. Never use matching commit messages or a green check from an older SHA as a substitute.
3. **Review-gate a PR that changes an interaction.** Its verdict carries a video of the change. A merge request covers it only after the operator has seen that evidence. Otherwise stop at merge-ready and wait for the operator's review.
4. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass, or with an unreviewed gate. A verified PR sitting above an unverified one is not landable. Report the ceiling as a PR number and say what breaks the chain.
5. **Merge only on a merge request.** "Ship it", "land", and "merge" are merge requests. "Is this safe to merge" asks for the report only, so stop after reporting which PRs are safe to merge and the ceiling. To merge, read the repository's allowed merge methods (`gh repo view --json squashMergeAllowed,mergeCommitAllowed,rebaseMergeAllowed`); when more than one is allowed and the user named none, ask which to use. For a stack joined with `gh stack link`, `gh stack merge <ceiling PR> --yes --merge-method <squash|merge|rebase>` lands the verified run in one operation and retargets the PRs above it; step 2 re-checks their verdicts before a later merge. Otherwise merge the verified run from the bottom, one PR at a time; GitHub retargets the next PR only when the merged branch is deleted. Confirm each merge with `gh pr view`. On either path, if the next PR did not retarget, or it still carries the merged PR's commits after a squash, stop: its rebase is a force-push, which pauses for the user, and afterwards step 2 re-checks every verdict above it.
6. **Never enable GitHub auto-merge.** It merges without a verdict. On a stack, only the root targets protected trunk. Every child targets its unprotected parent branch and already reads `CLEAN`, so GitHub would merge children into parents immediately and collapse the stack into itself. If a previous agent armed it, disarm with `gh pr merge <n> --disable-auto` and confirm the field is back off.
7. **Stop at the ceiling.** When the verified run is reported or merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new verdict for that PR.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, where each verdict is posted, what merged and how you confirmed it, and what the next gap needs.
