### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the rest.** For "ship it", "is this safe to merge", "land the stack", or "merge <PR>".

This is the half after PR Check and Triage. Triage reports whether a PR can merge. Shipping decides what is actually safe to merge. Green is not safe, and the gap between those two words is where this playbook lives.

1. **Verify every PR independently before merging anything.** One fresh Review worker per PR, not batched, each exercising the real surface ([control-ui](../../control-ui/SKILL.md) or [control-cli](../../control-cli/SKILL.md) as the change demands) against parent versus head. Each returns `PASS`, `PASS+NOTES` or `FAIL` and posts that verdict on its own PR with the screenshots or recording that prove it (`gh pr comment <number> --body-file <file> --attach <path>`), so the record outlives the chat. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Review-gate a PR that changes an interaction.** Its verifier also records a 30 to 60 second video of the change and attaches it with the screenshots. Stop at merge-ready and wait for the operator's review before merging. A merge request covers a review-gated PR only after the operator has seen its evidence. A PR that changes no interaction says so in its verdict.
3. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass, or with an unreviewed gate. A verified PR sitting above an unverified one is not landable, because merging it would pull the gap in underneath it. Report the ceiling as a PR number and say what breaks the chain.
4. **Re-check that the verdicts still describe the code.** A rebase rewrites every SHA above it and silently invalidates every verdict without touching a single check. Compare `git patch-id` at the verdict SHA against the current head before trusting an older verdict, and re-verify anything that actually drifted. Twenty-one verdicts went stale this way in one run with no signal at all.
5. **Report, then merge only on an explicit merge request.** Without one, stop after reporting which PRs are safe to merge and the ceiling. With one, read the repository's allowed merge methods (`gh repo view --json squashMergeAllowed,mergeCommitAllowed,rebaseMergeAllowed`); when more than one is allowed and the user named none, ask which to use. Merge the verified run from the bottom, one PR at a time, and confirm each merge with `gh pr view`. GitHub retargets the next PR only when the merged branch is deleted. If it did not retarget, or it still carries the merged PR's commits after a squash, stop: its rebase is a force-push, which pauses for the user, and afterwards step 4 re-checks every verdict above it.
6. **Never enable GitHub auto-merge.** It merges without a verdict. On a stack, only the root targets protected trunk. Every child targets its unprotected parent branch and already reads `CLEAN`, so GitHub would merge children into parents immediately and collapse the stack into itself. If a previous agent armed it, disarm with `gh pr merge <n> --disable-auto` and confirm the field is back off.
7. **Stop at the ceiling.** When the verified run is reported or merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1, not a judgment call you make at 3am.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, where each verdict is posted, what merged and how you confirmed it, and what the next gap needs.
